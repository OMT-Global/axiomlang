# SQLite v1 Contract

SQLite v1 defines the AxiOM-owned persistence contract for issue #1452. The
canonical machine-readable contract is
`stage1/compiler-contracts/snapshots/sqlite-v1.json`; its closed public shape is
`stage1/compiler-contracts/schemas/axiom.sqlite-v1.schema.json`.

This tranche is deliberately `contract_only`. It fixes the authority,
statement, row, transaction, migration, recovery, lifecycle, error, and audit
semantics that a runtime implementation must satisfy. It does not claim that
the current compiler can open or execute a SQLite database, and it does not
move the production-readiness row above `syntax_only`.

## Provider boundary

The public AxiOM surface is database-shaped, not a projection of SQLite C
types. A runtime may use Provider ABI v1 or an accepted built-in equivalent,
but neither route may expose pointers, SQLite handles, allocator callbacks,
provider-specific result codes, or connection structs to AxiOM code.

The runtime boundary owns opaque, provider-scoped, generation-tagged handles
for databases, prepared statements, row cursors, transactions, and
savepoints. Every operation validates provider, handle kind, generation, open
state, and parent relationship before dispatch. Closing a parent invalidates
its children. Dropping a database finalizes statements, rolls back active
transaction scopes, and then closes the provider connection. Qualification
fails on a live handle or unfinalized statement rather than treating a leak as
a warning.

## Database authority

Opening a database requires the `database.sqlite` capability and a canonical
authority record. The database identity is derived from the canonical
authority and database-file identity; logs and evidence use that digest rather
than a caller label or raw path.

SQLite v1 accepts only an anchored project-relative path or its canonical
`file` URI form. Ambient search, network URI schemes, symlink escape, and
non-regular existing targets fail before provider dispatch. Open mode is one
of:

- `read_only`;
- `read_write`, which additionally requires explicit write authority; or
- `create`, which additionally requires explicit write and create authority.

Normalization, root anchoring, symlink policy, target type, and requested mode
are checked as one fail-closed decision. Existing files must either be opened
handle-relative to that decision or have their opened identity revalidated
against the pre-authorized file identity. Create mode is stricter: it requires
a handle-relative prevalidated parent, no-follow traversal, and exclusive leaf
creation. Post-create identity inspection alone cannot authorize a new target.

## Prepared statements and typed values

SQL enters the runtime only as one prepared statement. Script batching and
implicit statement splitting are outside v1. Values are supplied through
separate indexed or named bindings and are never interpolated or reparsed as
SQL. Supported parameter and result kinds are:

- `null`;
- `bool`;
- `int64`;
- `float64`;
- UTF-8 `text`; and
- `bytes`.

Unknown bind names or indexes fail before dispatch as `bind_address`, while
unsupported types fail as `bind_type`. Every placeholder must be bound before
`step`; omission fails as `bind_missing` and is not implicit NULL,
while `FieldValue::null`-equivalent binding remains explicit. `reset` clears all
bindings as well as row state so a later execution cannot reuse stale values.
Text and byte limits are checked before copying into provider memory. The
statement lifecycle is `prepare -> bind -> step -> reset/finalize`; reset
clears runtime row state, and finalize invalidates every child cursor.

Rows use a bounded forward cursor. A row value is valid only until the next
step, reset, or finalize unless it is explicitly copied into an owned AxiOM
value. Columns may be selected by index or stable name. Type conversion is
explicit: an integer is not silently treated as text, and a type mismatch
returns `row_type` without advancing or corrupting the cursor.

## Transactions and savepoints

Top-level scopes support begin, commit, and rollback with explicit deferred,
immediate, or exclusive begin modes. Nested transaction syntax maps only to
savepoints. Savepoint names are generated by the runtime or validated as an
identifier; they are never accepted as executable SQL fragments.

Creating a savepoint opens an active child scope. `release` commits an
unpoisoned child into its parent and terminates the child handle. `rollback_to`
rolls back child changes, clears the child poison, and keeps the child active;
`rollback_to_and_release` terminates the child as rolled back. Dropping an
active savepoint has the same terminal rollback effect. A child failure does
not poison its parent after terminal child rollback. A failed statement poisons
only the current scope until rollback so later calls cannot accidentally commit
a partially failed sequence. Commit and rollback are terminal for the scope
handle and produce stable `transaction_state` errors when repeated or used out
of order.

## Migrations and provenance

SQLite v1 consumes the existing `sql_migration` artifact class only when the
artifact declares the `sqlite` dialect. The current SQL Migration Target v0
renders PostgreSQL and therefore does not yet supply executable SQLite input.
A compatible migration is identified by its artifact digest plus provenance
digest, applied in strict monotonic sequence, and recorded as immutable
migration ID, digest, and applied version. Application runs in one exclusive
transaction and either commits the entire migration or rolls it back.

A history row with the same migration ID and different content is
`migration_diverged`. Divergence fails before any new migration runs. This
connects runtime persistence to the generated migration and provenance
contracts without making [SQL Migration Target v0](sql-migration-target-v0.md)
itself execute database effects.

## Busy handling, cancellation, and recovery

Contention uses a bounded retry policy under one monotonic operation deadline;
an individual retry cannot reset the budget. Exhaustion reports
`busy_timeout`. Cancellation interrupts the provider operation and drains its
completion before a statement or database handle can be reused.

The v1 writer policy makes single-writer contention explicit. After a crash,
reopen observes either committed state or a structured recovery error; it
cannot report partial success. Corruption returns a stable `corruption` error
and never performs an implicit repair. A repair or restore workflow requires a
separate authorized operation and is outside this contract.

## Errors and audit boundary

Every failure has a stable kind, operation class, opaque runtime-issued request
identity, nullable authority and database identities, bounded redacted message,
and retryable flag. The request identity exists before authority resolution.
Authority identity is issued only after a successful authority decision and is
null for `capability_denied` and `invalid_authority`. Database identity remains
nullable through `open_failed`; it becomes required as soon as an authorized
open establishes the file identity. Implementations must not probe file identity
before authorization. The versioned kinds are:

- capability and authority denial;
- open, prepare, bind-address, missing-binding, bind-type, execute, and row-type failure;
- busy timeout and cancellation;
- transaction-state and migration divergence;
- corruption, closed handle, and provider fault.

Audit records may include request, authority, and database identities, operation
class, allow/deny decision, transaction depth, migration ID, and stable error kind. They must
never contain SQL text, parameter names or values, row values, credentials,
raw paths/URIs, or raw handles. This rule applies to success, denial, provider
failure, and recovery evidence.

## Contract fixtures and qualification

The contract names 15 mandatory fixture classes covering prepared bind/row
round trips, unknown bind addresses, missing bindings, unsupported bind types,
binding reset, capability denial, injection resistance, row typing, rollback
and savepoints, crash/reopen recovery, concurrent busy cancellation, corruption,
migration divergence, and handle leaks. The checker prevents removal or
weakening of any named boundary:

```bash
make stage1-sqlite-v1
make stage1-sqlite-v1-test
```

Runtime completion remains gated on executable versions of those fixtures,
the filesystem/provider/value/text dependencies, lifecycle and capability
denial evidence, worker/API integration, and repository qualification. Until
then, `scope.qualification` must remain `contract_only` and readiness must
remain `partial` at `syntax_only`.
